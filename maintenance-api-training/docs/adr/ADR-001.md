# ADR-001: Record status transitions transactionally

- **Status:** Accepted (target design; implementation is pending)
- **Date:** 2026-11-16
- **Decision owners:** Maintenance API maintainers
- **Related:** `docs/ERD.md`, `docs/openapi.yaml`, B4/B7 and status-transition notes in `docs/bugs.md`

## Context

A maintenance request moves through a small lifecycle (`new`, `assigned`, `in_progress`, `done`, `cancelled`). The current implementation updates `maintenance_requests.status` directly in `RequestStatusController` and does not retain who changed it, the previous value, the new value, the time, or a reason. Assignment also changes status to `assigned` inside `AssignTechnicianAction`.

This makes operational questions difficult to answer: who cancelled a visit, when work started, whether a request was reopened, and why a transition occurred. It also makes status changes and their audit records vulnerable to partial writes if implemented as separate database operations. The existing status Form Request validates the target enum but does not enforce a transition graph; the controller can currently move a `done` request back to `in_progress`.

The exercise requires a `request_status_histories` entity with actor, from/to states, timestamp, and reason.

## Decision drivers

- Every persisted status change must have a corresponding immutable audit event.
- The current state and its history event must commit or roll back together.
- Actor attribution must use the authenticated user when available.
- Assignment and ordinary status changes must follow the same audit convention.
- The design should fit the existing Laravel/Eloquent structure and remain testable.

## Considered options

### Option A — Update the request directly and omit history

**Pros:** smallest code change; no extra table or write; easy to understand.

**Cons:** no audit trail, no actor/reason, cannot reconstruct prior states, and cannot satisfy the exercise's required entity. Rejected.

### Option B — Eloquent model observer listens for `updated`

**Pros:** centralizes detection of status changes; catches updates from multiple controllers/actions; keeps controllers thin.

**Cons:** the observer has implicit side effects; the actor/reason are not naturally available in every update path; bulk updates bypass model events; test setup and event ordering are less explicit; it is easier to accidentally write history outside the transaction boundary. Viable if the application later adopts a strict domain-event/observer convention, but not selected now.

### Option C — Explicit status-transition action using a database transaction

A dedicated action (for example `ChangeRequestStatusAction`) receives the request, target status, authenticated actor, and optional reason. It locks/reloads the request, checks the transition graph, updates `status` and `completed_at`, and inserts the history row inside one `DB::transaction()`. Assignment uses the same transition-writing service/action when it changes status to `assigned`.

**Pros:** explicit inputs and side effects; transaction boundary is visible; actor/reason are available; state graph can be checked consistently; straightforward unit/feature tests; avoids hidden observer behavior.

**Cons:** callers must use the action rather than calling `update(['status' => ...])`; requires careful refactoring of assignment and status paths; row-lock behavior depends on the database engine (SQLite does not provide the same row-level locking semantics as MySQL).

## Decision

Choose **Option C**. All status mutations must go through an explicit domain action/service. The action performs the current-state check and writes the request plus its history event in the same database transaction. `request_status_histories` is append-only from the API's perspective. The authenticated user is stored as `changed_by`; `reason` is optional. Request creation should create an initial event with `old_status = NULL` and `new_status = 'new'`.

The transition graph for the initial implementation is:

- `new → assigned` or `cancelled`
- `assigned → in_progress` or `cancelled`
- `in_progress → done` or `cancelled`
- `done` and `cancelled` are terminal

The transition graph is a product rule and should be confirmed with the product owner before being treated as immutable policy.

## Consequences

### Positive

- Each committed state change has a corresponding actor/time/from/to record.
- A failure to write history rolls back the state update, and vice versa.
- Status rules live in one testable place rather than being duplicated across controllers.
- The API can expose a request's status timeline without guessing from timestamps.

### Negative / trade-offs

- Each transition adds a database write and an index-maintenance cost.
- Existing direct status writes must be removed or routed through the action; otherwise the audit trail can become incomplete.
- Deleting a request currently cascades to dependent records. If history must survive request deletion for compliance, the lifecycle policy must change to soft deletion/archive rather than cascade.
- Concurrency tests should run against the production database engine. SQLite feature tests alone cannot prove row-lock behavior.

## Implementation plan

1. Add `request_status_histories` migration with FK to request (`CASCADE`) and nullable actor FK to users (`SET NULL`), plus `(maintenance_request_id, created_at)` index.
2. Add `RequestStatusHistory` model and `MaintenanceRequest::statusHistories()` / `User::statusChanges()` relations.
3. Add `ChangeRequestStatusAction` that uses `DB::transaction()` and `lockForUpdate()`, validates the transition, updates `completed_at`, and inserts history.
4. Route assignment's `new → assigned` transition through the same mechanism; create initial `NULL → new` history on request creation.
5. Add `reason` validation to the status endpoint and include history in request detail/list only if needed by the client contract.
6. Add tests for successful transitions, invalid transitions, unauthorized actors, rollback when history insertion fails, initial history, assignment history, and terminal states.

## Verification / rollout

- Verify every code path that writes `maintenance_requests.status` uses the action (search for `status` updates and direct assignments).
- Assert one history row per successful transition and zero history rows after a rolled-back transition.
- Run the feature suite against SQLite for functional behavior and MySQL 8 for locking/concurrency behavior.
- Backfill existing requests with a clearly marked baseline event only if a trustworthy actor/time/reason can be determined. Otherwise do not invent historical actors; document a one-time `NULL → current_status` migration event as a system baseline with an explicit reason.

## Rejected alternatives

Direct updates without audit and implicit model observers were rejected for the reasons above. Revisit the observer option only if the codebase later standardizes domain events and can guarantee transactional event dispatch plus explicit actor/reason propagation.
